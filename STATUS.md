## M1 — Packet + simulator: APPROVED 2026-11-18 ("Start M2, defaults")

**Works**
- 50-byte alert message and 16-byte downlink: encode, decode, CRC
  (`vrw/packet.py`). Example hex in docs/01-PACKET-SPEC.md, generated by code.
- Trigger state machine with the two-signal rule, R-01 danger timer and local
  cancel, latched escalation (`vrw/trigger.py`). Illegal transitions raise.
- Store-and-forward outbox with retries, ALERT priority, optional file mirror.
- Simulated satellite link with latency, drops and canopy blackouts.
- Base receiver: dedupe, newest-event-wins, payload class, ACK/RESOLVE downlinks.
- 9 scenarios, all PASS (`python3 -m vrw run-all`); 28 unit tests pass in ~4 s
  (`python3 -m unittest`), including 300 randomized runs showing weak
  contact or vitals alone never escalate. Two deliberate safety-logic bugs
  were injected and both were caught by the tests.

**Doesn't / not yet**
- No dashboard (M2). No real sensor inputs (M3). No real modem, no hardened
  retry policy, no battery budget (M4).
- Every threshold is a PLACEHOLDER (vrw/thresholds.json).
- Satellite limits (340/270 bytes, 50-byte credit) not verified against
  current modem docs (D-08).

**Two safety bugs found by review and fixed with defaults (accepted 2026-11-18):**
- R-19: one ISF sensor could supply both signals and escalate alone in 7 min.
- R-20: a local cancel did not stop an ALERT already queued under canopy.

**Open for the owner:** none — R-16 to R-20 run on defaults (accepted 2026-11-18).

## M2 — Dashboard: APPROVED 2026-11-18 ("Approve, start M3")

R-16 to R-20 accepted on defaults.

**Works**
- `python3 -m dashboard` serves a local page at http://127.0.0.1:8765. It is the
  base station: alert state in plain words, toxin families and levels, why it
  escalated (including reasons added after dispatch), vitals, battery, sensor
  age, message age and link delay, offline position plot with distance and
  bearing from base, message log with retries and duplicates.
- Responder checklist keyed to the payload class and families, from
  `dashboard/checklist.json`: what the responder carries + reminders
  (ventilation support for 3FTx). All content marked PLACEHOLDER (R-08).
- "Responder on scene — close alert" sends RESOLVE down the simulated link;
  the alert shows closed only when the band confirms.
- R-18 banner when the local team cancels after a dispatch; R-20 count of
  late alerts ignored.
- `python3 -m vrw demo <scenario>` plays any scenario live into the dashboard.
- Gate: elapid alert + checklist reach the dashboard 23 s after escalation
  (< 60 s), checked by an automated test that runs a real dashboard server.
  41 tests pass; 9/9 scenarios pass. Checked by eye in a browser at desktop
  and phone width (no sideways scroll).

**Doesn't / not yet**
- Checklist content is placeholder until a toxinologist writes it.
- No real sensors (M3), no real modem or hardened retry (M4).
- Ticks on the reminder checklist are not saved (page memory only).
- Bug found and fixed during the M2 check: a normal close showed a false
  "recall the responder" banner (R-18 now triggers only on a local cancel).

**Ruled at approval:** R-21 "(dry bite)" removed; R-22 checklist stays fixed
at first alert.

**Next (M3):** sensor stand-ins — vitals from CSV and lateral-flow cassette
image → family code, wired into the state machine.

## M3 — Sensor stand-ins: APPROVED 2026-11-18 ("carry on"; R-23, R-24 on defaults)

R-21 and R-22 accepted on defaults at the M2 approval.

**Works**
- **Cassette reader** (`vrw/sensors/lateral_flow.py`): reads a PNG image of a
  test cassette with a PNG reader written in plain Python (`png.py`), so there
  is nothing to install. It finds the result window, checks the control line,
  measures each family line against the control, and outputs family + band
  0–4 in exactly the form the trigger already uses. A missing control line,
  an unexpected line, a missing window or an unreadable file gives INVALID,
  which counts for nothing. It reads the same result from shifted, brighter
  and darker images, and from an RGB copy re-encoded by macOS (also one saved
  through JPEG).
- **Vitals reader** (`vrw/sensors/vitals.py`): reads a CSV of SpO2, breathing
  rate, heart rate and skin temperature. Impossible values are dropped as
  artifacts; gaps are never filled. A "sustained" low now needs readings
  with no gap over 3 min (R-24).
- **Synthetic data** in `scenarios/data/` (5 cassette images, 2 vitals CSVs),
  rebuilt exactly by `python3 -m vrw make-data`; a test checks the files
  match the generator.
- **New commands:** `python3 -m vrw cassette <image>`, `vitals <csv>`,
  `make-data`. Scenarios take `vitals_csv` and `lfa_image`, so `run`,
  `run-all` and the live dashboard `demo` all use the stand-ins.
- **Gate (automated, `tests/test_m3.py`):**
  - `standin_contact_only` is fed by the cassette image and the vitals CSV
    (with a slipped probe, an SpO2 of 0, a 20-min gap and blank cells). It
    confirms the local signal from the image and never escalates.
  - `standin_systemic_vitals` holds the ISF reading flat, so its escalation at
    1 h 14 min has to come from the vitals CSV. It reaches the base 23 s
    later, FAMILY_MATCHED (3FTx, PLA2).
  - A check swaps the systemic CSV into the contact-only story and confirms
    it then escalates, so the contact-only pass is not an empty input path.
- 63 tests pass; 12/12 scenarios pass. Played into the live dashboard from
  another folder: the alert and families display correctly.

**Doesn't / not yet**
- Only synthetic images. A real phone photo would need finding and
  straightening the cassette first, plus a JPEG decoder (pinned library,
  R-11). The reader has never seen a real cassette, and its cut-offs
  (R-23) can only be set by testing real ones.
- The ISF toxin reading is still scripted (D-20): in-body sensing is
  simulated only.
- An invalid cassette read on its own sends nothing. The band ignores it
  correctly, but neither the wearer nor the base is prompted to retest. The
  dashboard's "Test invalid" tag only shows on a later message. The band has
  no screen in v1. This could go into M4 or later.
- Bug found and fixed during M3: an early reader, given an off-centre image
  with no control line, mistook the 3FTx line for the control line and
  reported the wrong family. It now measures from the window frame
  (D-18), and a test covers this case. A flipped or upside-down image
  was only barely caught, so the layout was made lopsided. Flipped images
  now always read INVALID (tested for every family and band).

**Open for the owner:** R-23 (how a cassette line becomes a level), R-24
(dropping bad vitals readings and refusing to bridge gaps). Both are
running on the defaults.

**Next (M4):** field hardening — hardened queue and retry policy, canopy
failure-mode script, battery budget, FIELD-RUNBOOK.md, optional real modem
(R-12), and the timed end-to-end field simulation.

## M4 — Field hardening: APPROVED 2026-11-19 ("Approve and confirm"; R-25 to R-28 confirmed)

R-23 and R-24 accepted on defaults ("carry on").

**Works**
- **Power-cycle safe.** The queue and the next message number are saved to
  flash after every change. A damaged file is set aside. Scenario
  `canopy_power_cycle`: power is lost for 2 min under canopy with an ALERT
  queued, and the ALERT still gets through.
- **Bug found and fixed:** after a reboot the band restarted its message
  numbers at 0, and the base, which dropped repeats by number, would have
  thrown away new alerts. Both sides are fixed (D-03, R-25). Every scenario
  now checks that no message number is used twice.
- **Retry policy (R-26):** urgent messages first and every 60 s; routine
  messages wait for signal and back off to 15 min; one schedule for the
  whole queue; at most 24 messages, urgent ones never dropped.
- **Live readings at send (D-21).** Found in the field run: an ALERT raised
  under canopy carried a 30-min-old position, and the responder walked to
  it. Now position, vitals and battery are refreshed when a queued message
  finally goes out.
- **Simulated link:** zones over time (open field → forest edge → canopy)
  and a 0–5 bar signal reading.
- **Responder model and RESPONDER_STATUS:** the base tells the band (and
  the dashboard shows) "dispatched / walking in / on scene" with minutes to
  go; a responder marker appears on the plot.
- **Tools:** `python3 -m vrw field`, `canopy`, `battery`;
  [docs/FIELD-RUNBOOK.md](docs/FIELD-RUNBOOK.md),
  [docs/BATTERY-BUDGET.md](docs/BATTERY-BUDGET.md).
- **Optional modem driver** `vrw/link/rockblock.py`: works against a fake
  modem; refuses a real port without an explicit flag.
- **D-08 verified** (generic web search, no project details): 340 bytes
  up, 270 down, 1 credit per 50 bytes. Also learned: an empty mailbox check
  costs a credit, and downlinks arrive only during the band's own sessions
  (D-23).
- **README** now has the full system description, "Start here", and an
  appendix naming every message field, state and threshold (a test keeps
  it complete).
- Found in the final check and fixed: after a power cycle the "refresh
  at send" rule wiped the saved position and vitals of a restored ALERT
  (no new fix yet). Now the saved values are kept until new readings exist
  (D-21). The responder model also no longer crashes if no message ever
  carried a position.
- 88 tests pass; 14/14 scenarios pass. The open-sky elapid alert still
  reaches the dashboard 23 s after escalation.

**Doesn't / not yet**
- The local alarm (R-27) is a logged event only; there is no buzzer or
  light hardware yet.
- The simulated signal reading is never wrong. On a real modem, a wrong
  0-bar reading could delay an urgent send by up to 5 min (R-26, tested).
- The simulator delivers base → band messages whenever there is sky; a
  real modem only gets them during its own sessions (D-23).
- The modem driver has never touched a real modem. The power figures are
  assumptions, not measurements.
- This was not a real outdoor field test: the "field run" is a simulation.

**Owner's instruction "take ownership of vision" (2026-11-18).** I read it
as handing me product direction, so I made and built these four calls,
all confirmed by the owner on 2026-11-19 (DECISIONS.md, "Delegation"):

  power cut, including the skin-fluid history. A close from base now works

- **R-27:** the band's local alarm comes on after an urgent message has
  been stuck 5 min.
- **R-28:** responder numbers stay as simulation assumptions.
